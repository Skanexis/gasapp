## K-1 · Перебор PIN вне телефона после одного вызова Keystore

**Было (схема v2).** Ключ базы = `HKDF(Argon2id(PIN) ‖ секрет)`. Секрет —
32 случайных байта, зашифрованных ключом Android Keystore. Ключ Keystore
не требовал ни подтверждения, ни разблокированного экрана и **отдавал
секрет в память приложения**.

**Атака.** Инструмент криминалистики или вредонос с root на изъятом
телефоне один раз вызывает Keystore от имени приложения и получает
секрет. Дальше миллион вариантов PIN перебирается на видеокартах: по
оценке в самом коде — пара часов. Счётчик «10 неверных PIN — стереть» не
участвует вовсе: он живёт в коде приложения.

**Стало (схема v3).** Растянутый PIN проходит 64 раунда HMAC-SHA256 внутри
Keystore ключом, который оттуда не извлекается (`TeeKey`), и только ответ
входит в ключ базы (`aegis_keystore::pin::bind_tee`). Ответ зависит от PIN,
поэтому его не получить один раз и не унести:

* каждая попытка перебора требует **этого** телефона;
* попытки идут по очереди — оборудование одно, видеокарты не помогут;
* на Android 11+ ключ работает только при разблокированном экране
  (`setUnlockedDeviceRequired`): запертый изъятый телефон не отвечает.

**Переход.** Сначала всегда пробуется v3, затем v2 и v1. Старая база
перешифровывается сразу, секрет v2 уничтожается, биометрия выключается:
в её конверте старый ключ. Прерванный переход человека не запирает: уже
перешифрованная база открывается первой же попыткой. Проверено на
эмуляторе на двух аккаунтах v2: переписка на месте, `aegis.hw` удалён.

**Цена.** Вход — 1,2 с на эмуляторе (Argon2 0,2 с, Keystore 0,8 с,
открытие 0,2 с).

**⚠️ Что остаётся.** Против разблокированного телефона под root шесть
цифр — это сутки-трое перебора на самом устройстве, а не годы.
Настоящая защита от такого противника — длинный PIN (см. «Рекомендации»).

## C-1 · Действия GitHub по изменяемым меткам рядом с ключом подписи

`actions/checkout@v4`, `dtolnay/rust-toolchain@stable` и другие — это
метки, которые владелец действия может переписать. Так в 2025 году
произошло с `tj-actions/changed-files`: переписанная метка вытаскивала
секреты из тысяч репозиториев.

В `release.yml` те же действия работают в задании, которому выдан ключ
подписи APK с паролями. Утёкший ключ — это «обновление», которое телефон
примет как настоящее.

**Исправлено:** все 13 действий во всех workflow закреплены за хешем
коммита, версия — в комментарии. Хеши сверены с разыменованными тегами:
три тега оказались аннотированными, и хеш объекта тега был бы неверным.
Dependabot (`github-actions`) обновляет закрепления.

## C-2 · Подписанный релиз из общего кэша

`Swatinem/rust-cache` восстанавливал `target/` в задании, которое потом
подписывает результат. Кэш общий для всех workflow репозитория. Тот, кто
может запустить сборку из ветки, мог положить в него свои
скомпилированные файлы — и они уехали бы в подписанный APK.

**Исправлено:** релиз собирается без кэша. Задание переведено в
окружение `release`.

⚠️ **Владельцу:** создать окружение `release` в настройках репозитория,
назначить обязательных подтверждающих и разрешить только теги `v*`. Без
этого строка `environment: release` лишь создаёт пустое окружение.

## C-3 · Gradle и зависимости без сверки хешей

* `gradle-wrapper.properties` без `distributionSha256Sum`: подменённый
  дистрибутив Gradle выполнил бы свой код при сборке.
* Зависимости Maven (AndroidX, Kotlin, JNA, CameraX…) не сверялись:
  подменённая библиотека попала бы в APK незамеченной.

**Исправлено:**

* SHA-256 дистрибутива — с `services.gradle.org`;
* `android/gradle/verification-metadata.xml` — SHA-256 481 компонента по
  всем задачам CI и релиза. Проверено подменой: испорченный хеш
  `androidx.core` останавливает сборку («Dependency verification failed»);
* задание `gradle-wrapper` в `security.yml` сверяет `gradle-wrapper.jar` со
  списком всех выпущенных версий. Сверено и вручную: это официальный jar
  Gradle 9.2.1.

⚠️ **Обновление зависимостей** теперь требует обновить и хеши:

```bash
./gradlew --write-verification-metadata sha256 help \
  :app:testGmsDebugUnitTest :app:testFossDebugUnitTest \
  :app:lintGmsRelease :app:lintFossRelease \
  :app:assembleFossRelease :app:assembleGmsRelease \
  :app:assembleFossDebugAndroidTest -PaegisAllowUnreleasable=true
./gradlew --write-verification-metadata sha256 :app:bundleGmsRelease -PaegisAllowUnreleasable=true
```

Новые строки в `verification-metadata.xml` проверять в запросе на слияние
так же внимательно, как код.

## L-1, L-2 · Перебор сессий мусорным конвертом

Конверт, не открывшийся как инициация, перебирался по всем сессиям (до
256). В каждой поддельный заголовок заставлял досчитать до 2000 ключей
цепочки и сделать два DH. Первый контакт стоит незнакомцу миллисекунды
работы, а очередь отдаётся по сотне конвертов: минуты процессора
получателя на каждый приём.

При этом подойти могла только одна сессия: сертификат отправителя обязан
совпасть с чатом (`certificate_matches`), остальные отбрасывались бы всё
равно. **Теперь** пробуется только сессия чата из сертификата. Незапечатанные
конверты не принимаются вовсе: сервер их не берёт, и положить такой в
очередь может только тот, кто держит сервер.

## T-1 · Подпись APK проверялась только в Центре безопасности

`AppSignature` сверял подпись установленного APK с эталоном из сборки,
но показывал итог только в Центре безопасности. Жертва поддельной копии
туда не заглянет — PIN она отдаёт раньше.

**Исправлено:** `TamperGuard` проверяет подпись на экране входа и
регистрации **до ввода PIN** и при несовпадении предупреждает: «Эта копия
может быть поддельной», с выбором «закрыть» или «продолжить». Запрещать
работу бессмысленно — пересобравший вырежет и запрет. Честный
собиратель из исходников получает в эталон свою подпись и этого окна не
видит.

## R-1 · Пустые списки после смены ключа базы

Чтения идут через отдельное соединение с базой (исправление зависаний
2026-09-29). Оно открывалось прежним ключом и после `rekey_storage` не
читало ничего: списки чатов и контактов были пусты до перезапуска
приложения — будто переписка пропала. Касалось и перехода v1→v2.
Найдено вживую при переходе на v3.

**Исправлено:** смена ключа переоткрывает читающее соединение новым
ключом, а чтения на время смены ждут. Тест
`reads_follow_the_new_key_after_rekey` проверен и в обратную сторону:
без исправления падает.

## R-2 · Вход ждал Tor

После открытия базы в фоне идёт пополнение предключей через Tor, и оно
держит сетевой замок. Следом шла локальная запись проверочного значения
хранилища — и ждала этот замок до 30 с. Теперь запись идёт через
локальное соединение. Вход на эмуляторе — около 5 с вместо 30.

## B-1 · AAB не собирался

`bundleGmsRelease` падал в AGP («Sequence contains more than one matching
element») из-за разбиения APK по архитектурам. Google Play принимает
только AAB. Теперь разбиение включается только для APK. Проверено:
в AAB `libaegis.so` без таблицы символов и отладочной информации.

⚠️ AAB собирать **отдельной** командой, не вместе с `assemble…Release`:
переключатель разбиения действует на весь запуск Gradle.

## Проверено и находкой не оказалось

| Что | Почему не находка |
|---|---|
| Состояние храповика при ошибке расшифровки | Меняется в копии; новое сохраняется только при успешном теге AEAD |
| Точки малого порядка X25519 | `was_contributory` на каждом DH |
| PQXDH | Все подписи предключей гибридные (XEdDSA + ML-DSA) и проверяются до вычислений; привязка ML-DSA к классической identity; транскрипт связывает обе identity, эфемерный ключ, SPK и шифротекст ML-KEM |
| Заголовок сообщения | Входит в AAD; nonce выводится из ключа сообщения |
| Пропущенные ключи | Не больше 1000 на шаг, 5000 всего, срок жизни 30 дней |
| Подписанные запросы к серверу | Подпись покрывает метод, путь, время и хеш тела; параметров строки запроса ни один подписанный маршрут не читает |
| Экспортированные компоненты | Только экран запуска; интентов извне не принимается |
| Резервная копия Android | `allowBackup=false`, `dataExtractionRules` |
| Открытый трафик | Запрещён (`usesCleartextTraffic=false`) |
| Снятие запрета снимков для скриншотов дизайна | Только при `BuildConfig.DEBUG` |
| Журналы | R8 вырезает `Log.*`; в коде журналов нет |
| Нативная библиотека в релизе | Без `.symtab` и отладочной информации |
| Ключ восстановления | 256 бит |
| Клавиатура | `IME_FLAG_NO_PERSONALIZED_LEARNING` на полях ввода |
| Ключ File Vault из одного PIN | Обёрнутые ключи файлов лежат в зашифрованной базе: без ключа базы перебирать нечего |

## Рекомендации — решения за владельцем

1. **Длинный PIN.** После K-1 шесть цифр держат против снятого файла и
   запертого телефона, но не против разблокированного телефона под root.
   Предложить при регистрации PIN из 8–12 цифр или фразу; шесть цифр
   оставить минимумом.
2. **Ключ подписи.** Создать офлайн, хранить в двух местах, в Google Play —
   Play App Signing (ключ загрузки заменяем, ключ приложения держит
   Google). Отпечаток сертификата опубликовать на сайте и в README:
   по нему люди сверяют скачанный APK.
3. **Настройки GitHub.** Окружение `release` с подтверждающими; защита
   ветки `main` (запросы на слияние, обязательные проверки CI);
   двухфакторный вход с аппаратным ключом у всех, у кого есть запись.
4. **Проверка подлинности клиента на сервере** (аттестация ключа при
   регистрации) отсечёт пересобранные копии от сервера, но и собранные из
   исходников, и F-Droid — если не вести список разрешённых подписей.
   Решение политики, не кода.

### Чего сознательно не делаем

* **Обфускация и защита от отладки как мера безопасности.** Код открыт,
  стойкость держится на ключах, а не на тайне кода (принцип Керкгоффса).
  R8 и так переименовывает классы приложения; большего противник с root
  не заметит.
* **Отказ работать на рутованных телефонах.** На них сидят и те, кого мы
  защищаем: GrapheneOS, CalyxOS, собственные прошивки. Центр безопасности
  честно показывает состояние устройства.
* **Play Integrity.** Закрытая служба Google — не для сборки F-Droid и не
  для тех, кто прячется от Google.
