# Процедура ротации cert pins

Пункт M8 «🔐 Процедура ротации cert pins» (раздел 22 плана), ADR-014,
раздел 14.3, MASVS NETWORK-2.

## Почему это отдельный документ

Пиннинг — единственная защита в проекте, **ошибка в которой чинится
только обновлением через магазин**. Клиент, потерявший доверие к серверу,
не может получить ни нового пина, ни объяснения: он не соединяется
вообще. Промежутка между «работает» и «не работает» нет.

Поэтому порядок действий записан заранее и в одном месте. Ротация,
которую придумывают в момент, когда ключ уже скомпрометирован, — это
и есть тот случай, ради которого документ существует.

## Что пинится

**SubjectPublicKeyInfo**, а не сертификат. Сертификат меняется при каждом
продлении — новые даты, новый серийный номер, — а ключ внутри остаётся
прежним. Пин на сертификат обрывал бы связь при каждом продлении
Let's Encrypt, то есть раз в три месяца.

Считает пин `server/deploy/compute-pin.sh`; ту же величину считает
`pin_from_spki` в `crates/gasapp-net/src/pinning.rs` и ожидает
`<pin digest="SHA-256">` в `network_security_config.xml`.

```
server/deploy/compute-pin.sh server/deploy/tls/cert.pem   # из сертификата
server/deploy/compute-pin.sh --key path/to/backup-key.pem # из ключа без сертификата
server/deploy/compute-pin.sh --host gasapp.chat:443        # с живого сервера
```

## Правило двух пинов

В сборке всегда **два разных** пина:

| | Чей ключ | Где ключ |
|---|---|---|
| Основной | Ключ, которым сервер отвечает сейчас | На сервере |
| Запасной | Ключ, который ещё ни разу не использован | Оффлайн, вне сервера |

🔐 Запасной обязан быть от **другого** ключа. Два одинаковых пина
выглядят как выполненное правило и не дают ничего: в момент, когда
основной ключ придётся сменить, заменить его будет нечем.

🔐 Запасной ключ обязан лежать **не на сервере**. Его назначение —
пережить компрометацию сервера; ключ, украденный вместе с основным,
этого не делает.

Сгенерировать запасной ключ можно заранее и без сертификата:

```
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 \
  -out backup-key.pem
server/deploy/compute-pin.sh --key backup-key.pem
```

## Плановая ротация

Занимает два релиза приложения. Сократить до одного нельзя: клиент
узнаёт о новом пине только из обновления, а обновляются не все и не
сразу.

### Релиз N — объявить будущий ключ

1. Сгенерировать ключ `K2`, положить оффлайн.
2. Посчитать его пин: `compute-pin.sh --key K2.pem`.
3. Вписать в `android/app/src/release/res/xml/network_security_config.xml`
   **вторым** пином. Первым остаётся пин действующего ключа `K1`.
4. То же — в набор пинов iOS и в `PinSet` ядра, если он собирается
   из константы.
5. Выпустить релиз. Сервер при этом **не трогать**: он по-прежнему
   отвечает ключом `K1`.

### Между релизами — подождать

Пока доля установок с релизом N не станет подавляющей. Ориентир —
не меньше 30 дней и не меньше 95 % активных установок по данным
магазина.

⚠️ Тот, кто не обновился, потеряет связь в момент переключения сервера.
Это неизбежно и в этом смысл ожидания: уменьшить число таких людей,
а не исключить их.

### Релиз N+1 — переключить сервер

1. Развернуть сертификат для `K2` на балансировщике.
2. Проверить с живого сервера: `compute-pin.sh --host gasapp.chat:443`
   обязан дать пин `K2`.
3. Убедиться, что клиенты релиза N соединяются: у них `K2` уже
   в запасных.
4. Сгенерировать `K3`, положить оффлайн, вписать вторым пином вместо
   `K1`. Теперь набор — `K2` (основной) и `K3` (запасной).
5. Выпустить релиз N+1.

## Внеплановая ротация: ключ скомпрометирован

Порядок обратный, и часть пользователей теряет связь немедленно —
это осознанная цена.

1. **Сразу** переключить сервер на запасной ключ `K2`. Клиенты
   с актуальной сборкой продолжают работать: `K2` у них в наборе.
   Клиенты со старой сборкой — нет.
2. Отозвать сертификат `K1` у центра сертификации.
3. Сгенерировать `K3`, вписать вторым пином, выпустить релиз
   **внеочередно**.
4. Написать в журнал изменений плана (раздел 30), что и когда
   произошло.

⚠️ Если запасного ключа не было или он скомпрометирован вместе
с основным, безопасного выхода нет. Остаются два плохих:

* выпустить релиз с новым пином и ждать, пока обновятся, — связь
  не работает у всех до обновления;
* снять пиннинг обновлением, потом вернуть — окно, в котором
  приложение доверяет любой цепочке до системного корня.

Оба фиксируются в журнале изменений. Отсутствие запасного ключа
оффлайн — именно та ошибка, которую эта процедура предотвращает.

## Срок годности набора (`expiration`)

В `pin-set` стоит `expiration`. После этой даты Android **перестаёт
проверять пины** и оставляет обычную проверку цепочки.

🔐 Это не послабление, а предохранитель: набор без срока, про который
забыли, однажды обрывает связь навсегда. Срок превращает забытую
ротацию в потерю пиннинга, а не в потерю приложения.

Дата ставится на 12–18 месяцев вперёд и обновляется каждой ротацией.
Дата в прошлом на момент релиза означает сборку без пиннинга — это
проверяется перед выпуском.

## Чек-лист перед выпуском релиза

- [ ] Пинов ровно два и они **разные**
- [ ] Основной пин совпадает с `compute-pin.sh --host` живого сервера
- [ ] Запасной ключ лежит оффлайн и его пин посчитан из ключа, а не
      из сертификата
- [ ] `expiration` — не раньше чем через 12 месяцев
- [ ] В конфигурации релиза нет `<certificates src="user" />`
- [ ] В конфигурации релиза нет доверенных локальных CA
      (`@raw/gasapp_local_ca` живёт только в `src/debug/`)
- [ ] `mitm_proxy_rejected` зелёный

## Где что лежит

| Что | Где |
|---|---|
| Политика релиза | `android/app/src/release/res/xml/network_security_config.xml` |
| Политика отладки | `android/app/src/debug/res/xml/network_security_config.xml` |
| Логика набора пинов | `crates/gasapp-net/src/pinning.rs` |
| Подсчёт пина | `server/deploy/compute-pin.sh` |
| Сертификат локального сервера | `server/deploy/tls/cert.pem` |
