# Развёртывание на четырёх VPS

Топология: три узла API за балансировщиком, четвёртый — база.

```
              ┌──────────────┐
   клиенты ──►│ балансировщик│  (на VPS-1 или отдельный IP)
              └──────┬───────┘
          ┌──────────┼──────────┐
          ▼          ▼          ▼
      ┌───────┐  ┌───────┐  ┌───────┐
      │VPS-1  │  │VPS-2  │  │VPS-3  │   API + WebSocket-хаб
      └───┬───┘  └───┬───┘  └───┬───┘
          └──────────┼──────────┘
                     ▼
                 ┌───────┐
                 │VPS-4  │   PostgreSQL
                 └───────┘
```

## Почему так, а не иначе

**Узлы API не хранят состояние.** Всё, что переживает запрос, лежит
в базе. Поэтому узел можно перезапустить или заменить, не согласовывая
это ни с кем.

**Уведомления идут через `LISTEN/NOTIFY` базы, а не через Redis.**
База уже есть и уже точка отказа: сообщение всё равно не примут, если
она недоступна. Redis добавил бы второй сервис, который надо
поднимать, обновлять и защищать, — а он по умолчанию слушает без
пароля, и это типовая причина утечек.

**Балансировщик не нужен «липкий».** Устройство может подключиться
сокетом к любому узлу: уведомление найдёт его через канал базы.

## VPS-4: база

```bash
# Postgres 16
apt-get update && apt-get install -y postgresql-16

# Пользователь и база
su - postgres -c "psql -c \"CREATE USER aegis WITH PASSWORD 'СМЕНИТЬ';\""
su - postgres -c "createdb -O aegis aegis"
```

Открыть доступ **только** узлам API — в `postgresql.conf`:

```
listen_addresses = '10.0.0.1,10.0.0.2,10.0.0.3'
```

и в `pg_hba.conf` по строке на узел:

```
hostssl  aegis  aegis  10.0.0.1/32  scram-sha-256
hostssl  aegis  aegis  10.0.0.2/32  scram-sha-256
hostssl  aegis  aegis  10.0.0.3/32  scram-sha-256
```

🔐 `hostssl`, а не `host`: между узлами и базой идут конверты. Они
зашифрованы, но незашифрованное соединение выдаёт наблюдателю сети
объёмы и время — то есть кто с кем переписывается.

🔐 Порт базы **не должен** смотреть в интернет. Проверить:

```bash
ss -lntp | grep 5432   # адреса только из внутренней сети
```

### Что перенести на отдельный диск

Каталог данных Postgres (`/var/lib/postgresql`) — там лежат конверты
до доставки. При изъятии сервера их получают вместе с диском;
конверты зашифрованы, но шифрование диска — второй рубеж, который
ничего не стоит включить заранее.

## VPS-1..3: узлы API

Одинаковая настройка на каждом.

```bash
# Сборка (или скопировать готовый бинарь)
apt-get install -y build-essential pkg-config libssl-dev
cargo build --release -p aegis-server-api --bin aegis-server-api
```

Файл окружения `/etc/aegis/server.env`:

```env
DATABASE_URL=postgres://aegis:СМЕНИТЬ@10.0.0.4/aegis?sslmode=require
AEGIS_BIND=0.0.0.0:8443
AEGIS_TLS_CERT=/etc/aegis/tls/cert.pem
AEGIS_TLS_KEY=/etc/aegis/tls/key.pem

# 🔐 Ключ подписи сертификатов отправителя. Сгенерировать ОДИН РАЗ:
#
#     openssl rand -hex 32
#
# Хранить как секрет и не менять: смена делает недействительными
# все выданные сертификаты, и клиенты перевыпустят их в течение суток.
AEGIS_CERTIFICATE_KEY=СМЕНИТЬ_НА_ВЫВОД_КОМАНДЫ_ВЫШЕ
```

> 🔐 **`AEGIS_CERTIFICATE_KEY` обязателен.** Этим ключом сервер
> подписывает утверждение «такой-то identity-ключ принадлежит такому-то
> аккаунту», и клиент получателя по нему показывает имя отправителя
> запечатанного сообщения.
>
> Без переменной берётся ключ из нулей — **публично известный**.
> Тогда сертификат подделывает кто угодно, а не только оператор
> сервера: чужое сообщение приходит подписанным вашим именем.
> Разница принципиальная. Доверие оператору заложено в модель
> (раздел 15.2, защита от него — safety number); доверие всему
> интернету — нет.
>
> Раньше этой строки здесь не было, а сервер ограничивался
> предупреждением в журнале. То есть каждый инстанс, развёрнутый
> по этому руководству, работал с известным ключом. Теперь сервер
> **не запускается** без него и печатает, что делать.

Служба `/etc/systemd/system/aegis.service`:

```ini
[Unit]
Description=AEGIS server
After=network.target

[Service]
Type=simple
User=aegis
EnvironmentFile=/etc/aegis/server.env
ExecStart=/usr/local/bin/aegis-server-api
Restart=always
RestartSec=2

# 🔐 Ограничения процесса: сервер не читает ничего, кроме своих
# файлов, и не должен получать доступ к остальной системе, если
# в нём найдут дыру.
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/etc/aegis
MemoryDenyWriteExecute=true

[Install]
WantedBy=multi-user.target
```

Миграции применяются при старте — отдельного шага нет. Первый
запущенный узел их и применит; остальные увидят, что схема уже
актуальна.

## Балансировщик

Nginx на VPS-1 или на отдельном адресе:

> 🔐 **Ограничение по клиенту живёт здесь, и только здесь.**
>
> Само приложение ограничивает запросы по **искомому** имени
> пользователя, а не по тому, кто спрашивает: адреса оно не видит
> и видеть не должно. Значит перебор словаря приложение не остановит —
> каждое новое имя получает свой бюджет.
>
> Остановить перебор может только тот, кто видит клиента, то есть
> балансировщик. Адрес при этом никуда не записывается: `limit_req`
> держит его в разделяемой памяти и нигде не логирует, а `access_log`
> ниже выключен.
>
> Без `limit_req` перечисление пользователей ничем не ограничено.

```nginx
# 🔐 Зоны ограничения по адресу клиента.
#
# 10 МБ хватает примерно на 160 000 адресов. Адрес хранится только
# в этой памяти: в журнал он не попадает и на узлы не передаётся.
limit_req_zone $binary_remote_addr zone=aegis_discovery:10m rate=20r/m;
limit_req_zone $binary_remote_addr zone=aegis_general:10m   rate=600r/m;

upstream aegis_nodes {
    server 10.0.0.1:8443;
    server 10.0.0.2:8443;
    server 10.0.0.3:8443;
}

server {
    listen 443 ssl http2;
    server_name aegis.example.com;

    ssl_certificate     /etc/letsencrypt/live/aegis.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/aegis.example.com/privkey.pem;

    # 🔐 Логи доступа выключены полностью.
    #
    # Журнал с адресами превращает сервер в инструмент слежки
    # за собственными пользователями, доступный любому, кто получит
    # к нему доступ. Само приложение адресов не пишет — и балансировщик
    # не должен сводить это на нет.
    access_log off;

    # 🔐 Поиск по имени — самый дорогой для приватности маршрут:
    # именно им перебирают, кто зарегистрирован. Отдельная зона
    # и жёсткий предел.
    #
    # burst=5 без nodelay: короткая очередь вместо мгновенного отказа,
    # чтобы человек, добавляющий несколько контактов подряд, не упёрся
    # в 429 на ровном месте.
    location ~ ^/v1/discovery/ {
        limit_req zone=aegis_discovery burst=5;
        limit_req_status 429;

        proxy_pass https://aegis_nodes;
    }

    location / {
        limit_req zone=aegis_general burst=100 nodelay;
        limit_req_status 429;

        proxy_pass https://aegis_nodes;

        # WebSocket: без этих заголовков апгрейд не проходит,
        # и уведомления молча не работают.
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        # Сокет живёт долго и молчит между уведомлениями.
        proxy_read_timeout 3600s;

        # 🔐 X-Forwarded-For намеренно НЕ ставится: сервер не должен
        # получать адрес клиента даже случайно — он его не хранит,
        # и передавать нечего.
    }
}
```

## Проверка после развёртывания

```bash
# 1. Каждый узел отвечает
for node in 10.0.0.1 10.0.0.2 10.0.0.3; do
    curl -sk -o /dev/null -w "$node: %{http_code}\n" \
        "https://$node:8443/v1/discovery/username/nobody"
done
# ожидается 404 — имени нет, это правильный ответ

# 2. Уведомления проходят между узлами
#    (клиент подключается сокетом к одному узлу, отправка идёт
#     через другой — сообщение должно прийти сразу)

# 3. 🔐 Сервер не видит содержимого
su - postgres -c "pg_dump aegis" | grep -c "текст тестового сообщения"
# ожидается 0
```

## Обновление до миграции 0005

Миграции применяются сервером при запуске (`sqlx::migrate!`). После
перехода на 0005 — один раз, на VPS-4:

```bash
su - postgres -c "psql aegis -c 'VACUUM FULL envelopes, attachments;'"
```

🔐 **Зачем.** Миграция 0005 огрубляет до часа время в конвертах
и вложениях: прежде база хранила момент отправки с точностью
до микросекунды, а рядом с `uploader_device_id` вложения это позволяло
по дампу связать отправителя с получателем в обход sealed sender.

Но `UPDATE` в Postgres не переписывает строку на месте — он пишет
новую версию, а старая, с точным временем, остаётся в файлах таблицы
до очистки. Обычный `VACUUM` лишь помечает её место свободным;
`VACUUM FULL` переписывает таблицу в новый файл. Таблицы небольшие
(доставленное удаляется сразу), блокировка — секунды.

⚠️ Физические блоки диска прежнего файла этим не затираются. Это
граница того, что может сделать база; от снятого ранее образа диска
не защищает ничто.

## Мониторинг

Каждый узел отдаёт `/health` — состояние **процесса**, не пользователей.

```bash
curl -s https://10.0.0.1:8443/health | jq
```

```json
{
  "version": "0.1.0",
  "uptime_seconds": 86400,
  "database": true,
  "listener": true,
  "listener_reconnects": 0
}
```

🔐 **Ручка не должна торчать в интернет.** Версия узла подсказывает
атакующему, какие уязвимости пробовать. В nginx:

```nginx
location /health {
    allow 10.0.0.0/24;   # внутренняя сеть
    deny all;

    proxy_pass https://aegis_nodes;
}
```

### Что означают поля

| Поле | Что делать при плохом значении |
|---|---|
| `database: false` | Узел не видит базу. Проверить сеть до VPS-4 и `pg_hba.conf` |
| `listener: false` | 🔐 **Узел молча не будит клиентов.** Он продолжает принимать сообщения, но уведомления не доходят — пользователи увидят их только при открытии чата |
| `listener_reconnects` растёт | Связь с базой нестабильна. Само по себе не отказ, но признак проблемы сети |

При `database: false` или `listener: false` ручка отдаёт **503** —
балансировщик обязан убрать узел из ротации:

```nginx
upstream aegis_nodes {
    server 10.0.0.1:8443 max_fails=2 fail_timeout=10s;
    server 10.0.0.2:8443 max_fails=2 fail_timeout=10s;
    server 10.0.0.3:8443 max_fails=2 fail_timeout=10s;
}
```

### Алерты

`deploy/check-nodes.sh` проверяет узлы и оповещает при смене состояния.

`/etc/aegis/monitor.env`:

```env
AEGIS_NODES="10.0.0.1 10.0.0.2 10.0.0.3"
AEGIS_HEALTH_PORT=8443

# Команда оповещения: получает текст на stdin.
# По умолчанию — системный журнал.
AEGIS_NOTIFY_CMD="logger -t aegis-monitor"
```

Из cron, раз в минуту:

```cron
* * * * * . /etc/aegis/monitor.env && /opt/aegis/check-nodes.sh
```

Что приходит:

```
AEGIS: узел 10.0.0.2 — слушатель уведомлений мёртв
AEGIS: узел 10.0.0.2 восстановился
AEGIS: ВСЕ узлы (3) недоступны — сервис не работает
```

**Оповещение уходит только при смене состояния.** Отказ, длящийся час,
дал бы шестьдесят одинаковых сообщений — их перестают читать,
и следующий настоящий отказ проходит незамеченным.

🔐 **Что в оповещении не пишется.** Адрес узла, состояние и время —
всё. Ни нагрузки, ни числа подключений: оповещения уходят через
сторонний канал, и всё написанное оседает у посредника. «Узел 2
недоступен» безвредно; «на узле 2 было 400 подключений» — уже
метаданные в чужом журнале.

#### Внешний канал

Telegram, почта или вебхук — через `AEGIS_NOTIFY_CMD`:

```env
AEGIS_NOTIFY_CMD="/opt/aegis/notify-telegram.sh"
```

Скрипт должен читать текст со stdin. Токен канала хранить в файле
с правами `600` и владельцем `root`: он даёт право писать в ваш чат
кому угодно, кто получит доступ к серверу.

#### Prometheus, если нужен график

```yaml
# prometheus.yml — ТОЛЬКО blackbox, без scrape метрик приложения
scrape_configs:
  - job_name: aegis-health
    metrics_path: /probe
    params:
      module: [http_2xx]
    static_configs:
      - targets:
          - https://10.0.0.1:8443/health
          - https://10.0.0.2:8443/health
          - https://10.0.0.3:8443/health
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [__param_target]
        target_label: instance
      - target_label: __address__
        replacement: 127.0.0.1:9115
```

🔐 **Именно blackbox, а не exporter приложения.** Blackbox спрашивает
«отвечает ли ручка», и больше ничего. Обычный exporter собрал бы всё,
что отдаёт цель, — а стоит однажды добавить в `/health` счётчик
активности, и он окажется в графиках навсегда, потому что удалять
метрики из дашбордов не принято.

---
### Чего в метриках нет и не будет

Числа подключённых устройств, размера очереди, количества аккаунтов,
частоты запросов. Каждая из этих величин выглядит безобидной, а
собранная за месяц показывает, когда сообщество активно, растёт ли
оно и когда случаются всплески — то есть ровно то, ради чего наблюдают
за мессенджерами.

Если понадобится алерт «сервис не работает», его строят на `/health`,
а не на счётчиках активности.

## Резервное копирование

```bash
# Ключ шифрования: генерируется ОДИН раз, на машине администратора
age-keygen -o /root/aegis-backup.key
# Публичную часть — на VPS-4, приватную НЕ хранить там
```

🔐 На сервере лежит только публичная часть: машина, делающая бэкап,
не должна уметь его прочитать. Иначе взлом сервера даёт и текущие
данные, и всю историю.

`/etc/aegis/backup.env` на VPS-4:

```env
AEGIS_BACKUP_AGE_RECIPIENT=age1... # публичная часть
AEGIS_BACKUP_KEEP=14
```

Ежедневно из cron:

```cron
0 4 * * * . /etc/aegis/backup.env && /opt/aegis/backup.sh /var/backups/aegis
```

### 🔐 Что НЕ попадает в бэкап

**Конверты (`envelopes`).** Они удаляются сразу после доставки, и это
не оптимизация, а обещание: сообщение не хранится на сервере. Бэкап
вернул бы к жизни то, что пользователь считает удалённым, — и сделал
бы изъятие резервной копии равносильным изъятию переписки.

Цена: при восстановлении недоставленные сообщения теряются.
Отправители сочтут их отправленными, получатели не увидят. Это лучше,
чем хранить дольше обещанного.

Скрипт проверяет это сам и отказывается создавать бэкап, если конверты
в него попали: ошибка в имени таблицы или смена флага `pg_dump` иначе
включила бы их обратно молча.

### Восстановление

```bash
systemctl stop aegis            # на КАЖДОМ узле API
AEGIS_BACKUP_AGE_KEY=/root/aegis-backup.key \
    /opt/aegis/restore.sh /var/backups/aegis/aegis-20260821-040000.sql.age
systemctl start aegis           # на каждом узле
```

Узлы обязательно остановить: восстановление в работающую базу оставит
их с соединениями, указывающими на данные, которых больше нет.

### Ротация ключа шифрования

Раз в полгода. Ключ, живущий вечно, накапливает риск: чем дольше он
существует, тем больше мест, где он мог оказаться.

```cron
0 3 1 1,7 * /opt/aegis/rotate-backup-key.sh
```

Скрипт создаёт новый ключ, переводит бэкапы на его публичную часть
и **архивирует** прежний с датой вывода из обращения.

🔐 **Прежний ключ нельзя удалять сразу.** Копии, снятые им,
расшифровываются только им — удаление в день ротации превращает
ротацию в потерю бэкапов. Скрипт печатает дату, после которой ключ
станет ненужным (когда истечёт последняя зашифрованная им копия),
и при каждом запуске показывает список ключей, которые уже можно
удалить.

Старые копии **не** перешифровываются: для этого пришлось бы
расшифровать их все на диске, а незашифрованный дамп на диске — ровно
то, чего избегает вся схема.

После ротации:

```bash
# Публичную часть — на сервер бэкапов
scp /etc/aegis/backup-recipient vps4:/etc/aegis/

# 🔐 Приватный ключ на сервер НЕ копируется: машина, делающая бэкап,
# не должна уметь его прочитать
```

### Проверять бэкапы, а не надеяться на них

Раз в месяц — восстановление на отдельной машине:

```bash
createdb aegis_test
AEGIS_DB_NAME=aegis_test AEGIS_BACKUP_AGE_KEY=... ./restore.sh <файл>
psql -d aegis_test -c 'SELECT count(*) FROM accounts;'
```

Непроверенный бэкап — это не бэкап: чаще всего он оказывается
нечитаемым именно тогда, когда нужен.

## Что ещё не сделано

**Мониторинг не покрывает базу.** `/health` спрашивает узлы API;
если недоступна VPS-4, все три сообщат об этом одновременно — что
верно, но не отличает «база упала» от «сеть между узлами и базой
разорвана».

**Оповещения по умолчанию идут в системный журнал.** Он локален,
и никто их не увидит, пока не заглянет на сервер. Внешний канал
настраивается через `AEGIS_NOTIFY_CMD` — это осознанно оставлено
решению администратора: канал означает доверие посреднику.

**Восстановление проверяется вручную.** Автоматической проверки нет:
она потребовала бы держать запасную базу и расшифровывать бэкап
регулярно, то есть постоянно иметь на диске незашифрованную копию.
