# AEGIS: развёртывание и эксплуатация сервера

Руководство оператора: от четырёх пустых VPS до работающего, укреплённого
и наблюдаемого сервера — и что делать потом, каждый день и в плохой день.

Читать по порядку. Каждый шаг заканчивается **проверкой**: не переходите
к следующему, пока она не прошла. Сломанный шаг, найденный сразу, —
пять минут; найденный через месяц — инцидент.

> 🔐 так отмечено то, без чего защита не работает. Пропускать нельзя.
> ⚠️ так — ошибки, которые уже случались, и места, где легко ошибиться.
> 🔴 так — то, что обрывает связь у всех пользователей сразу.

## 1. Как устроено

```
                       интернет                        Tor
                          │                             │
                     443 (TLS 1.2/1.3,             onion-сервис
                     пин ключа в приложении)       (контейнер)
                          │                             │
              ┌───────────▼─────────────────────────────▼──────┐
              │ VPS-1  nginx: :443 публичный, 10.0.0.1:8444 onion│
              │        лимиты по клиенту, журналы выключены     │
              └───────────┬─────────────────────────────────────┘
                          │ TLS 1.3, сертификат узла проверяется
            ┌─────────────┼─────────────┐   (внутренний центр, имя aegis-node)
            ▼             ▼             ▼
       10.0.0.1:8443 10.0.0.2:8443 10.0.0.3:8443    узлы API (Rust)
            └─────────────┼─────────────┘
                          │ TLS 1.3 verify-full + сертификат клиента + пароль
                          ▼
                    10.0.0.4:5432  PostgreSQL 16     VPS-4 (+ админ-центр,
                                                     резервные копии)
```

В руководстве: балансировщик — на VPS-1 рядом с первым узлом; внутренняя
сеть — `10.0.0.0/24`; домен — `aegis.example.com`. Замените на свои.

### Почему так

**Узлы не хранят состояние.** Всё, что переживает запрос, лежит в базе:
узел можно перезапустить или заменить, ни с кем не согласовывая.

**Уведомления — через `LISTEN/NOTIFY` базы, а не Redis.** База уже есть
и уже точка отказа. Redis — второй сервис, который надо поднимать,
обновлять и защищать, а по умолчанию он слушает без пароля — типовая
причина утечек.

**Балансировщику не нужна «липкость».** Устройство подключается сокетом
к любому узлу: уведомление найдёт его через канал базы.

### 🔐 Что защищается и от кого

| Угроза | Что её останавливает |
|---|---|
| Перебор имён (кто зарегистрирован) | `limit_req` в nginx — только он видит клиента |
| Подмена сервера, MITM на пути телефона | Пин ключа TLS в приложении; ключ под контролем оператора |
| Сосед или хостер во внутренней сети | TLS с проверкой сертификата на **каждой** внутренней связи |
| Утёкший пароль базы | Без ключа сертификата клиента он бесполезен (и наоборот) |
| Дыра в коде узла | Песочница systemd: нечего писать, нечего запускать, некуда ходить |
| Взлом машины → слежка за пользователями | Журналов с адресами нет нигде: nginx, узлы, база |
| Изъятие резервной копии → переписка | Конверты и вложения в копию не попадают; копия зашифрована ключом, которого на сервере нет |
| Тихий отказ (узел жив, но не будит клиентов) | Монитор `/health` → `listener: false` |
| Подмена бинаря на сервере | Монитор сверяет суммы каждые 2 минуты |

### 🔐 Принципы, которые не нарушаются ради удобства

* **Никаких журналов с адресами клиентов.** Ни `access_log`, ни
  `error_log` в nginx (он пишет адрес в каждую строку ошибки), ни
  `log_connections` в Postgres. Сервер, который пишет адреса, — это
  инструмент слежки за собственными пользователями, доступный любому,
  кто его получит.
* **Никакого `X-Forwarded-For`.** Узел не получает адрес клиента даже
  случайно — nginx затирает и свои заголовки, и присланные клиентом.
* **Никаких метрик активности.** Число подключений, сообщений, аккаунтов,
  частота запросов — собранные за месяц, они показывают ровно то, ради
  чего наблюдают за мессенджерами. Мониторинг отвечает на вопрос
  «работает ли», а не «насколько активно».
* **Секреты — не в окружении.** Учётные данные systemd: их не видно
  в `/proc/*/environ`, `systemctl show` и отчётах о падениях.

### Что где лежит в репозитории

| Файл | Куда на сервере | Зачем |
|---|---|---|
| `hardening/harden-host.sh` | запускается один раз | SSH, sysctl, брандмауэр, автообновления |
| `pki/internal-ca.sh` | **только** машина администратора | Внутренний удостоверяющий центр |
| `postgres/90-aegis.conf`, `pg_hba.conf` | VPS-4 `/etc/postgresql/16/main/` | TLS, журнал без метаданных, доступ |
| `systemd/aegis-server.service` | узлы `/etc/systemd/system/` | Узел в песочнице |
| `nginx/aegis.conf`, `aegis-upstream.inc` | VPS-1 `/etc/nginx/` | Балансировщик |
| `certbot/aegis-cert.sh` + `systemd/aegis-cert.*` | VPS-1 `/opt/aegis/certbot/` | Сертификат с запиненным ключом |
| `systemd/aegis-admin.service`, `aegis-reports.*` | VPS-4 | Админ-центр и уведомления о жалобах |
| `monitor/aegis-monitor.sh` + `systemd/aegis-monitor.*` | все `/opt/aegis/monitor/` | Монитор |
| `check-nodes.sh` | VPS-1 `/opt/aegis/` | Здоровье узлов (вызывается монитором) |
| `notify-telegram.sh` | все `/opt/aegis/` | Канал оповещений |
| `backup.sh`, `restore.sh`, `rotate-backup-key.sh` + `systemd/aegis-backup.*` | VPS-4 `/opt/aegis/` | Резервные копии |
| `onion/`, `webtunnel/` | VPS-1 / отдельные VPS | Tor |

## 2. Что понадобится

* **Четыре VPS** с Debian 12 или Ubuntu 22.04/24.04, во внутренней сети
  хостера (`10.0.0.0/24`). Узлам — 2 ядра и 2 ГБ, базе — 4 ГБ и SSD.
* **Домен**, A/AAAA-запись которого указывает на VPS-1.
* **Машина администратора** — ваш ноутбук или, лучше, отдельная машина,
  которая не ходит по сайтам. На ней живут ключи, которых нет на серверах.
  Нужны: `openssl`, `age`, `ssh`, Rust (для сборки).
* **Носитель для оффлайн-ключей** — зашифрованная флешка (две, в разных
  местах): ключ внутреннего центра, запасной ключ TLS, ключ резервных
  копий.
* **Бот Telegram** для оповещений (или почта/вебхук — см. шаг 7).
* Учётная запись администратора с SSH-ключом на каждой VPS
  (`adduser alice && usermod -aG sudo alice`, ключ — в
  `~alice/.ssh/authorized_keys`).

### 🔐 Где какой секрет живёт

| Секрет | Где живёт | Где его быть не должно |
|---|---|---|
| Ключ внутреннего центра `ca.key` | Оффлайн-носитель | Любой сервер |
| Запасной ключ TLS (второй пин) | Оффлайн-носитель | Любой сервер — его смысл в том, чтобы пережить взлом сервера |
| Приватный ключ резервных копий (age) | Машина администратора + оффлайн | VPS-4 — машина, снимающая копию, не должна уметь её прочитать |
| `AEGIS_CERTIFICATE_KEY` | `/etc/aegis/credentials/` на узлах (root, 600) + оффлайн-копия | git, файлы окружения, чаты |
| Пароль базы | `/etc/aegis/credentials/` на узлах и VPS-4 | git, `server.env` |
| Основной ключ TLS | `/etc/aegis/tls/public/privkey.pem` на VPS-1 (600) + оффлайн-копия | Где-либо ещё |
| Токен админ-центра | Менеджер паролей оператора; на сервере — только SHA-256 | На сервере в открытом виде |
| Токен бота Telegram | `/etc/aegis/credentials/telegram` (root, 600) | Командная строка, окружение |
| Ключ onion-адреса | Том Docker `aegis-onion-keys` + резервная копия | — |

## 3. Шаг 0. Машина администратора: ключи и секреты

Всё в этом шаге делается **на машине администратора**, не на серверах.

### 3.1. Внутренний удостоверяющий центр

```bash
export AEGIS_PKI_DIR=/media/aegis-offline/pki      # оффлайн-носитель
server/deploy/pki/internal-ca.sh init

# База: имя, которое узлы проверяют, и её адрес
server/deploy/pki/internal-ca.sh server db    aegis-db   10.0.0.4

# Узлы: у всех одно имя aegis-node — его проверяет nginx
server/deploy/pki/internal-ca.sh server node1 aegis-node 10.0.0.1
server/deploy/pki/internal-ca.sh server node2 aegis-node 10.0.0.2
server/deploy/pki/internal-ca.sh server node3 aegis-node 10.0.0.3

# Клиентский сертификат базы: CN = роль базы
server/deploy/pki/internal-ca.sh client aegis
```

🔐 **Зачем свой центр, если сеть внутренняя.** «Внутренняя» сеть VPS —
это сеть хостера: соседи, ошибки изоляции, сам хостер. Шифрование без
проверки сертификата (`sslmode=require`, `curl -k`) от того, кто встал
посредине, не защищает: он предъявит свой сертификат, и его примут.
А между узлами и базой идут конверты и время их доставки — то есть кто
кому пишет. Публичный центр (Let's Encrypt) не годится: внутренним
адресам он сертификат не выдаст, а каждый выданный попадает в публичный
журнал Certificate Transparency вместе с именами.

### 3.2. Остальные секреты

```bash
cd /media/aegis-offline

# Пароль базы (hex — без символов, которые пришлось бы экранировать в URL)
openssl rand -hex 24 > db-password

# Ключ подписи сертификатов отправителя — ОДИН РАЗ, навсегда
openssl rand -hex 32 > aegis-certificate-key

# Ключ резервных копий
age-keygen -o aegis-backup.key          # приватный — остаётся здесь
age-keygen -y aegis-backup.key          # публичный (age1…) — пойдёт на VPS-4

# 🔐 Запасной ключ TLS — второй пин приложения. На сервер НЕ попадает.
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out tls-backup-key.pem
server/deploy/compute-pin.sh --key tls-backup-key.pem    # → запасной пин

# Токен админ-центра: в менеджер паролей
openssl rand -base64 32
```

> 🔐 **`AEGIS_CERTIFICATE_KEY` обязателен и не меняется.** Им сервер
> подписывает утверждение «такой-то identity-ключ принадлежит такому-то
> аккаунту», и по нему клиент получателя показывает имя отправителя
> запечатанного сообщения. Без ключа сервер **не запускается**: прежде
> он брал ключ из нулей — публично известный, — и сертификат подделывал
> кто угодно, а не только оператор. Доверие оператору заложено в модель
> (защита от него — safety number); доверие всему интернету — нет.
> Смена ключа делает недействительными все выданные сертификаты;
> клиенты перевыпустят их в течение суток.

### 3.3. Сборка сервера

Собирать на машине администратора (или в CI), а не на серверах: на
сервере не должно быть компилятора — это готовый инструмент для того,
кто туда попадёт.

```bash
cd server
cargo build --release --locked -p aegis-server-api -p aegis-server-admin
sha256sum target/release/aegis-server-api target/release/aegis-server-admin
```

Суммы записать — по ним монитор будет замечать подмену.

## 4. Шаг 1. Укрепление каждой машины

На каждой VPS, под своим пользователем, с открытой **второй** сессией SSH
на случай ошибки:

```bash
scp -r server/deploy alice@vps1:/tmp/aegis-deploy
ssh alice@vps1
sudo /tmp/aegis-deploy/hardening/harden-host.sh \
    --role lb,node --admin alice --lb 10.0.0.1 --onion 10.0.0.1
```

| Машина | Команда |
|---|---|
| VPS-1 (балансировщик + узел 1) | `--role lb,node --lb 10.0.0.1 --onion 10.0.0.1` |
| VPS-2, VPS-3 | `--role node --lb 10.0.0.1` |
| VPS-4 (база + админ-центр) | `--role db --nodes "10.0.0.1 10.0.0.2 10.0.0.3"` |

Дополнительно: `--ssh-from <ваша сеть>` закрывает SSH для всего
интернета, кроме вас; `--auto-reboot` разрешает ночную перезагрузку после
обновления ядра (на узлах — да, их три; на базе и балансировщике лучше
перезагружать вручную по оповещению монитора).

Что делает скрипт:

* **SSH:** только ключи, без root, без пересылки агента и X11, пускает
  только `--admin`; разрешена лишь локальная пересылка — для туннеля
  к админ-центру. 🔐 Вход по паролю выключается, только если у
  администратора есть ключ и sudo, — иначе отказ до изменений.
  Конфигурация проверяется `sshd -t` до перезапуска.
* **Ядро:** закрыты адреса ядра и `dmesg`, `ptrace` чужих процессов
  (в памяти узла — ключ подписи), BPF для непривилегированных; защита
  сети. `log_martians` намеренно выключен: он пишет адреса источников.
* **Дампы памяти — нигде.** В них были бы ключи.
* **Журнал:** 14 дней, не дублируется в `/var/log/syslog`.
* **Брандмауэр по роли:** снаружи открыто только нужное этой машине.
* **Автообновления безопасности** и перезапуск служб после обновления
  библиотек (`needrestart`).
* **Пользователи служб:** `aegis`, `aegis-admin`, `aegis-monitor`.

**Проверка** (не закрывая старую сессию):

```bash
ssh alice@vps1 'sudo -v && echo ok'                         # новый вход работает
ssh -o PubkeyAuthentication=no alice@vps1                   # → Permission denied
sudo ufw status verbose
sudo sshd -T | grep -E '^(passwordauthentication|permitrootlogin) '   # no, no
```

## 5. Шаг 2. База (VPS-4)

```bash
sudo apt-get install -y postgresql-16 postgresql-client-16    # (Ubuntu 24.04: postgresql)

# Роль и база
sudo -u postgres psql -c "CREATE ROLE aegis LOGIN PASSWORD '$(cat db-password)';"
sudo -u postgres createdb -O aegis aegis
```

Пароль вводить с машины администратора через `ssh … 'cat > …'`, а не
набирать в истории оболочки: `history` сохраняет его в файл.

**Сертификаты** (с машины администратора):

```bash
ssh alice@vps4 'sudo install -d -m 755 -o postgres /etc/postgresql/aegis-tls'
scp $AEGIS_PKI_DIR/{ca.pem,db.pem,db.key} alice@vps4:/tmp/
ssh alice@vps4 'cd /tmp && sudo install -o postgres -m 644 ca.pem db.pem /etc/postgresql/aegis-tls/ \
    && sudo install -o postgres -m 600 db.key /etc/postgresql/aegis-tls/ && rm -f ca.pem db.pem db.key'
```

**Настройка:**

```bash
sudo install -m 644 /tmp/aegis-deploy/postgres/90-aegis.conf /etc/postgresql/16/main/conf.d/
sudo install -m 640 -o postgres /tmp/aegis-deploy/postgres/pg_hba.conf /etc/postgresql/16/main/pg_hba.conf
sudo systemctl restart postgresql
```

Что в них и почему:

* `listen_addresses = 'localhost,10.0.0.4'` — **собственные** адреса
  сервера базы. ⚠️ Прежде здесь стояли адреса узлов: к чужим адресам
  Postgres привязаться не может и не запустился бы. Кому можно
  подключаться, решают `pg_hba.conf` и брандмауэр.
* `ssl_min_protocol_version = TLSv1.3` — клиенты базы только узлы.
* 🔐 `pg_hba.conf`: узлам — `hostssl … scram-sha-256 clientcert=verify-full`:
  нужны **и** пароль, **и** сертификат внутреннего центра с CN = `aegis`.
  Пароль, утёкший из копии конфигурации, без ключа бесполезен — и
  наоборот. Всё, что не разрешено явно, отвергается последними строками.
* 🔐 **Журнал без метаданных:** без адресов подключений, без текста
  запросов, `log_error_verbosity = terse`. Именно в `DETAIL` Postgres
  пишет значения — «Key (username)=(alice) already exists»: имя, которое
  кто-то пытался занять, оседало бы в журнале.

**Шифрование диска.** Каталог данных (`/var/lib/postgresql`) хранит
конверты до доставки. Они зашифрованы, но если хостер позволяет — диск
данных под LUKS. Это второй рубеж при изъятии диска, а не защита от
того, кто изъял работающую машину вместе с памятью.

**Проверка:**

```bash
ss -lntp | grep 5432           # только 127.0.0.1 и 10.0.0.4, не 0.0.0.0
sudo -u postgres psql -tAc 'show ssl'                   # on
sudo -u postgres psql -tAc 'show log_error_verbosity'   # terse

# С узла, когда он будет готов (шаг 3): без сертификата — отказ
psql "host=10.0.0.4 dbname=aegis user=aegis sslmode=verify-full sslrootcert=/etc/aegis/pki/ca.pem"
# → FATAL: connection requires a valid client certificate
```

## 6. Шаг 3. Узлы API (VPS-1..3)

Одинаково на каждом узле; отличаются адрес и сертификат (`nodeN`).

**Бинарь и суммы** (с машины администратора):

```bash
scp server/target/release/aegis-server-api alice@vps1:/tmp/
ssh alice@vps1 'sudo install -m 755 /tmp/aegis-server-api /usr/local/bin/ && rm /tmp/aegis-server-api \
    && sha256sum /usr/local/bin/aegis-server-api | sudo tee /etc/aegis/checksums.sha256'
```

Сравните сумму с той, что получили при сборке.

**Сертификаты и секреты:**

```bash
# Открытое — читается всеми
scp $AEGIS_PKI_DIR/{ca.pem,client-aegis.pem,node1.pem} alice@vps1:/tmp/
ssh alice@vps1 'cd /tmp && sudo install -d -m 755 /etc/aegis/tls \
  && sudo install -m 644 ca.pem client-aegis.pem /etc/aegis/pki/ \
  && sudo install -m 644 node1.pem /etc/aegis/tls/node.pem && rm -f ca.pem client-aegis.pem node1.pem'

# 🔐 Секреты — только root, 600; службе их отдаёт systemd
cat $AEGIS_PKI_DIR/node1.key        | ssh alice@vps1 'sudo install -m 600 /dev/stdin /etc/aegis/credentials/node-key.pem'
cat $AEGIS_PKI_DIR/client-aegis.key | ssh alice@vps1 'sudo install -m 600 /dev/stdin /etc/aegis/credentials/db-client-key.pem'
cat aegis-certificate-key           | ssh alice@vps1 'sudo install -m 600 /dev/stdin /etc/aegis/credentials/aegis_certificate_key'
echo "postgres://aegis:$(cat db-password)@10.0.0.4:5432/aegis?sslmode=verify-full&sslrootcert=/etc/aegis/pki/ca.pem&sslcert=/etc/aegis/pki/client-aegis.pem&sslkey=/run/credentials/aegis-server.service/db_client_key" \
    | ssh alice@vps1 'sudo install -m 600 /dev/stdin /etc/aegis/credentials/database_url'
```

⚠️ `AEGIS_CERTIFICATE_KEY` **одинаковый на всех узлах**: сертификат,
выданный одним узлом, проверяется по ключу, общему для кластера.

**Несекретная настройка** `/etc/aegis/server.env`:

```env
# 🔐 Внутренний адрес ЭТОГО узла, не 0.0.0.0.
AEGIS_BIND=10.0.0.1:8443
AEGIS_TLS_CERT=/etc/aegis/tls/node.pem
# Лимиты частоты делятся на число узлов: без этого кластер из трёх
# пропускал бы втрое больше заявленного.
AEGIS_CLUSTER_NODES=3
```

Ключа TLS здесь нет: юнит передаёт путь к нему в каталоге учётных
данных сам (`AEGIS_TLS_KEY=%d/tls_key`).

**Служба:**

```bash
sudo install -m 644 /tmp/aegis-deploy/systemd/aegis-server.service /etc/systemd/system/
# Если внутренняя сеть не 10.0.0.0/24:
#   sudo systemctl edit aegis-server   →  [Service]
#                                         IPAddressAllow=
#                                         IPAddressAllow=localhost 10.1.0.0/24
sudo systemctl daemon-reload
sudo systemctl enable --now aegis-server
```

Миграции применяются при старте: первый узел их применит, остальные
увидят, что схема актуальна.

**🔐 Узел отказывается запускаться небезопасно** и печатает, что
исправить: без TLS, без `AEGIS_CERTIFICATE_KEY`, **от root**, с базой
на другой машине без `sslmode=verify-full` (или `verify-ca`). Обойти
можно только явным `AEGIS_ALLOW_INSECURE=1` — для тестов, не для боя.
`sslmode=require` не принимается: он шифрует, но принимает любой
сертификат.

**Что даёт песочница** (`systemd/aegis-server.service`): система только
для чтения, писать некуда; запускать можно только системные библиотеки;
ни одной привилегии; чужих процессов не видно; системные вызовы — только
нужные службе; код в памяти не подменяется (`MemoryDenyWriteExecute`);
сеть — **только внутренняя** (`IPAddressAllow`): взломанный процесс
не выгрузит данные наружу и не скачает инструменты; дампов памяти нет.

**Проверка:**

```bash
systemctl is-active aegis-server
journalctl -u aegis-server -n 5 --no-pager      # «сервер AEGIS слушает по TLS»
systemd-analyze security aegis-server.service | tail -1    # ≈ 1.0 OK (без песочницы — 9.6)
ss -lntp | grep 8443                             # только 10.0.0.N, не 0.0.0.0

# Здоровье — с проверкой сертификата узла (с балансировщика):
curl -s --cacert /etc/aegis/pki/ca.pem --resolve aegis-node:8443:10.0.0.1 https://aegis-node:8443/health
# {"version":"…","database":true,"listener":true,…}

# 🔐 Снаружи узел недоступен (с машины вне внутренней сети):
curl -sk -m 5 https://<публичный-адрес-узла>:8443/health \
    && echo "ОШИБКА: узел доступен в обход балансировщика" || echo "закрыт — правильно"
```

> ⚠️ Прежде в этом руководстве стояло `AEGIS_BIND=0.0.0.0:8443` без шага
> с брандмауэром — порт каждого узла смотрел в интернет, а всё, что
> держит балансировщик (лимиты, предел тела), обходилось прямым запросом.

## 7. Шаг 4. Балансировщик, сертификат и пины

### 7.1. nginx

```bash
sudo apt-get install -y nginx certbot
sudo rm -f /etc/nginx/sites-enabled/default
sudo install -m 644 /tmp/aegis-deploy/nginx/aegis.conf /etc/nginx/conf.d/aegis.conf
sudo install -m 644 /tmp/aegis-deploy/nginx/aegis-upstream.inc /etc/nginx/aegis-upstream.inc
sudo sed -i 's/aegis.example.com/<ваш домен>/g' /etc/nginx/conf.d/aegis.conf
```

Что в конфигурации и почему:

* 🔐 **Ограничение по клиенту живёт здесь, и только здесь.** Приложение
  ограничивает поиск по **искомому** имени, а не по тому, кто ищет: адреса
  оно не видит и видеть не должно. Перебор словаря остановит только тот,
  кто видит клиента. Без `limit_req` перечисление пользователей ничем
  не ограничено. Адрес при этом хранится только в разделяемой памяти.
* 🔐 **Журналы выключены — оба.** `access_log off` адреса не убирает:
  nginx пишет адрес в **каждую** строку `error_log`, в том числе на каждый
  отказ `limit_req`. Перебор имён превратился бы в журнал адресов тех,
  кто перебирал, — и тех, кто просто добавлял контакты подряд.
* 🔐 **Узел проверяется.** `proxy_ssl_verify on` с внутренним центром
  и именем `aegis-node`; только TLS 1.3. Узел, предъявивший чужой
  сертификат, получает 502 — проверено.
* 🔐 **Чужое имя — обрыв рукопожатия** (`ssl_reject_handshake`):
  сканеры, обходящие адреса, не получают сертификат и не связывают IP
  с доменом.
* **TLS 1.2 нужен:** minSdk приложения — 28 (Android 9), а TLS 1.3
  в платформе — с Android 10. Шифры 1.2 — только ECDHE + AEAD.
* **Без билетов сессии** (`ssl_session_tickets off`): утечка ключа
  билетов раскрыла бы все сессии за время жизни процесса.
* **Пределы:** тело 4 МБ, вложения 102 МБ, таймауты медленных клиентов,
  200 соединений с адреса (с запасом — многие приходят с одного выхода Tor).
* `/health` снаружи — 404: версия узла подсказывает, какие уязвимости
  пробовать.

### 7.2. Сертификат с запиненным ключом

> 🔴 **Почему не обычный certbot.** Приложение пинит **ключ** сертификата
> (SPKI), а certbot по умолчанию при каждом продлении создаёт новый ключ.
> Первое же продление — через 60 дней после запуска — оборвало бы связь
> у всех установок разом, и починить это могло бы только обновление
> приложения. `--reuse-key` держится на одной строке в файле продления,
> которую легко потерять, а вернуть прежний ключ в цепочку certbot потом
> нечем.
>
> Поэтому ключ — свой и не меняется, а certbot только подписывает запрос
> (`certonly --csr`): `certbot/aegis-cert.sh`. Перед тем как nginx увидит
> сертификат, проверяется, что его ключ — из набора пинов.

```bash
sudo install -d -m 755 /opt/aegis/certbot
sudo install -m 755 /tmp/aegis-deploy/certbot/aegis-cert.sh /opt/aegis/certbot/
printf 'AEGIS_DOMAIN=aegis.example.com\nAEGIS_ACME_EMAIL=ops@example.com\n' \
    | sudo install -m 644 /dev/stdin /etc/aegis/cert.env

# Основной ключ + заглушка (nginx без файлов не стартует); печатает пин
sudo /opt/aegis/certbot/aegis-cert.sh bootstrap
#   пин основного ключа: B9QLNyYk…=
```

**Набор пинов** `/etc/aegis/pins.txt` — ровно тот, что в приложении:

```
# основной — ключ на этом сервере
B9QLNyYkdKaHQfktOOJHznH5p2Q8+eWILykW2LfPhzA=
# запасной — tls-backup-key.pem на оффлайн-носителе
<пин из шага 3.2>
```

🔐 **Оффлайн-копия основного ключа:** `/etc/aegis/tls/public/privkey.pem`
— на носитель. Потеря машины без копии = смена ключа = обрыв связи
у тех, кто не обновился.

```bash
sudo systemctl enable --now nginx
sudo /opt/aegis/certbot/aegis-cert.sh renew --force   # первый настоящий сертификат
sudo /opt/aegis/certbot/aegis-cert.sh status

# Продление — своим таймером; пакетный certbot.timer ВЫКЛЮЧИТЬ
sudo systemctl disable --now certbot.timer
sudo install -m 644 /tmp/aegis-deploy/systemd/aegis-cert.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now aegis-cert.timer
```

### 7.3. 🔴 Пины в приложении

В `android/app/src/release/res/xml/network_security_config.xml` (и в
наборе iOS/ядра) — **два разных** пина: основной и запасной, и
`expiration` не раньше чем через 12 месяцев. Полная процедура и
чек-лист — `docs/ops/cert-pin-rotation.md`.

> ⚠️ На 2026-10-02 в релизной конфигурации стоят заглушки
> (`AAAA…=`, `BBBB…=`) и `expiration="2027-01-01"` — меньше 12 месяцев.
> Релиз с ними не выпускать.

**Проверка:**

```bash
sudo nginx -t
# Пин живого сервера = основной пин
server/deploy/compute-pin.sh --host aegis.example.com:443
# Чужое имя — обрыв
curl -sk --resolve x.example:443:<IP VPS-1> https://x.example/ ; echo "rc=$?"     # rc=35
# Запрос доходит до узла
curl -s -o /dev/null -w '%{http_code}\n' https://aegis.example.com/v1/discovery/username/nobody   # 404
curl -s -o /dev/null -w '%{http_code}\n' https://aegis.example.com/health                         # 404
```

## 8. Шаг 5. Tor: onion-адрес и мосты

Tor в приложении — по умолчанию. Две вещи делают его надёжным.

### 8.1. Onion-адрес сервера

Приложение в режиме Tor ведёт соединения к onion-сервису: **без
выходного узла** (его никто не видит и не может подменить) и без
зависимости от публичного адреса. TLS и пины остаются в силе — onion
их не заменяет, а дополняет.

> 🔴 **Onion — через балансировщик, а не напрямую на узел** (аудит S-2).
> Tor включён по умолчанию, то есть **большинство** клиентов ходит
> через onion — и всё, что держит nginx, для них не действовало бы:
> предел тела, таймауты, ограничение соединений, предел поиска по имени.
> Onion пробрасывает TCP как есть: телефон видит тот же сертификат, что
> и без Tor, и пины совпадают.

Отдельный `server` на `10.0.0.1:8444` в `aegis.conf` — только для onion.
Лимиты там общие на весь вход: адреса клиента за onion нет, все приходят
с адреса контейнера Tor, и `limit_req` по адресу отрезал бы всех разом.

```bash
AEGIS_UPSTREAM=10.0.0.1:8444 docker compose -f server/deploy/onion/docker-compose.yml up -d
docker compose -f server/deploy/onion/docker-compose.yml logs onion | grep "AEGIS onion"
# → AEGIS onion: <56 знаков>.onion:443
```

Адрес вписывается в сборку: `./gradlew assembleRelease -PaegisServerOnion=<адрес>.onion:443`.
Адрес задаёт сборка, а не сервер: подменить его сервер не может.

🔐 Ключ onion-адреса — в томе `aegis-onion-keys`: в резервную копию
вместе с ключами TLS. Потерять — сменить адрес во всех сборках.

Узел защищается и сам: подписанное тело — не больше 4 МиБ, одновременно
не больше восьми загрузок вложений, каждая не дольше 20 минут. Это вторая
линия, не замена балансировщику.

**Если Tor заблокирован у самого сервера** (в журнале `Stuck at 5% (conn)`)
— через мосты; проще всего snowflake, строки уже в образе:

```bash
AEGIS_TOR_BRIDGES=snowflake AEGIS_UPSTREAM=10.0.0.1:8444 \
    docker compose -f server/deploy/onion/docker-compose.yml up -d --build
```

Свои мосты — строками в `AEGIS_TOR_BRIDGES` через `\n` или файлом
`server/deploy/onion/bridges/bridges.txt` (не в git). Транспорты
собираются в образе из исходников Tor Project через proxy.golang.org.
Это только сервер: в приложение они не попадают (ADR-005).

Для разработки то же работает с локальным сервером
(`AEGIS_BIND=0.0.0.0:8443`, `AEGIS_UPSTREAM=host.docker.internal:8443`).

### 8.2. Свои мосты WebTunnel

Там, где Tor блокируют, приложение идёт по лестнице: напрямую →
встроенные мосты → **свежие мосты от Tor Project** (moat, без капчи).
Свои мосты — запас на случай, если закроют и moat.

Мост — обычный сайт с сертификатом Let's Encrypt, внутри которого по
секретному пути идёт Tor:

```bash
# на VPS с доменом, указывающим на него, открытыми 80 и 443:
cd server/deploy/webtunnel && ./new-bridge.sh bridge1.example.com admin@example.com
# → webtunnel [2001:db8::…]:443 ОТПЕЧАТОК url=https://bridge1.example.com/… ver=0.0.1
```

Строку — в `android/tor/bridges.txt` или, чтобы не светить мосты
в открытом репозитории, в свой файл:
`./gradlew assembleRelease -PaegisBridgesFile=/путь/bridges.txt`.

**Чем больше и разнообразнее, тем лучше:** разные хостеры, страны, домены.
Блокировщик закрывает мосты по одному.

⚠️ Мост и сервер AEGIS — у **разных** операторов: тот, кто видит и вход
в мост, и сервер, может сопоставить время соединений. На машину моста
тоже — `harden-host.sh` (роль `lb`: ей нужны только 80 и 443).

## 9. Шаг 6. Админ-центр

Ставится на VPS-4: связь с базой — unix-сокет, ни база, ни админ-центр
не выходят в сеть. Слушает только `127.0.0.1:8480` — другой адрес
отказ запуска.

```bash
scp server/target/release/aegis-server-admin alice@vps4:/tmp/
ssh alice@vps4
sudo install -m 755 /tmp/aegis-server-admin /usr/local/bin/ && rm /tmp/aegis-server-admin
sha256sum /usr/local/bin/aegis-server-admin | sudo tee -a /etc/aegis/checksums.sha256

# Сокет и пароль (строка `local aegis aegis scram-sha-256` в pg_hba)
echo "postgres://aegis:<пароль>@localhost/aegis?host=/var/run/postgresql" \
    | sudo install -m 600 /dev/stdin /etc/aegis/credentials/admin_database_url

# Токен — из менеджера паролей; на сервере остаётся только SHA-256
read -rs TOKEN && printf '%s' "$TOKEN" | /usr/local/bin/aegis-server-admin hash-token \
    | sudo install -m 600 /dev/stdin /etc/aegis/credentials/admin_token_sha256; unset TOKEN

sudo install -m 644 /tmp/aegis-deploy/systemd/aegis-admin.service /etc/systemd/system/
sudo install -m 644 /tmp/aegis-deploy/systemd/aegis-reports.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now aegis-admin aegis-reports.timer
```

**Вход** — туннелем SSH со своей машины:

```bash
ssh -N -L 8480:127.0.0.1:8480 alice@vps4
# браузер: http://127.0.0.1:8480
```

`aegis-reports.timer` раз в 10 минут сообщает о новых жалобах — только
число: кто и на кого, видно в самом админ-центре.

**Проверка:**

```bash
systemd-analyze security aegis-admin.service | tail -1     # ≈ 0.9 SAFE
ss -lntp | grep 8480                                        # только 127.0.0.1
```

## 10. Шаг 7. Мониторинг и оповещения

### 10.1. Канал: бот Telegram

1. `@BotFather` → `/newbot` → токен.
2. Создать закрытую группу, добавить бота, написать в группу что-нибудь;
   `https://api.telegram.org/bot<TOKEN>/getUpdates` → `chat.id` (вида `-100…`).
3. На **каждой** машине:

```bash
printf 'TOKEN=123456:ABC…\nCHAT_ID=-100123456789\n' \
    | sudo install -m 600 /dev/stdin /etc/aegis/credentials/telegram
sudo install -m 755 /tmp/aegis-deploy/notify-telegram.sh /opt/aegis/
echo "AEGIS: проверка канала" | sudo /opt/aegis/notify-telegram.sh
```

🔐 Токен не попадает в командную строку curl (там его видит любой
пользователь машины в `ps`) — адрес уходит через `--config` на stdin.
Файл читается, а не исполняется. Без Telegram — пустой файл: оповещения
пойдут в журнал (`journalctl -t aegis-notify`), но тогда их никто
не увидит, пока не зайдёт на сервер.

🔐 **Что в оповещениях.** Состояние и время — всё. Ни нагрузки, ни числа
подключений, ни адресов: оповещения оседают у посредника. «Узел 2
недоступен» безвредно; «на узле 2 было 400 подключений» — уже метаданные
в чужом журнале. Входы по SSH сообщаются именем, без адреса.

### 10.2. Монитор

На каждой машине:

```bash
sudo install -d -m 755 /opt/aegis/monitor
sudo install -m 755 /tmp/aegis-deploy/monitor/aegis-monitor.sh /opt/aegis/monitor/
sudo install -m 755 /tmp/aegis-deploy/check-nodes.sh /opt/aegis/          # VPS-1
sudo install -m 644 /tmp/aegis-deploy/monitor/monitor.env.example /etc/aegis/monitor.env
sudo editor /etc/aegis/monitor.env
sudo install -m 644 /tmp/aegis-deploy/systemd/aegis-monitor.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now aegis-monitor.timer
```

| | VPS-1 (lb + node) | VPS-2, VPS-3 | VPS-4 |
|---|---|---|---|
| `AEGIS_ROLES` | `"lb"` | `"node"` | `"db"` |
| `AEGIS_UNITS` | `"nginx aegis-server docker"` | `"aegis-server"` | `"postgresql aegis-admin"` |
| `AEGIS_ALLOWED_PORTS` | `"22 80 443 8443 8444"` | `"22 8443"` | `"22 5432"` |
| `AEGIS_WATCH_CERTS` | `"/etc/aegis/tls/node.pem"` | `"/etc/aegis/tls/node.pem"` | `"/etc/postgresql/aegis-tls/db.pem"` |
| Прочее | `AEGIS_DOMAIN`, `AEGIS_PIN_EXPIRATION`, `AEGIS_NODES` | — | `AEGIS_PROBE_PUBLIC=aegis.example.com:443` + `/etc/aegis/pins.txt` |

🔐 **Машины следят друг за другом.** VPS-1 проверяет узлы. VPS-4
проверяет публичный вход **снаружи** балансировщика: если умрёт сам
VPS-1, его монитор замолчит, а монитор базы — нет. Если умрёт VPS-4,
об этом скажут узлы (`database: false`) через монитор VPS-1.

### 10.3. Что приходит и что делать

| Оповещение | Что значит | Что делать |
|---|---|---|
| `узел … — недоступен` | Процесс не отвечает | `systemctl status aegis-server`, журнал на узле |
| `узел … — не видит базу` | Нет связи с VPS-4 | Сеть до VPS-4, `pg_hba.conf`, сертификаты (срок!) |
| `узел … — слушатель уведомлений мёртв` | 🔐 **Узел молча не будит клиентов**: принимает сообщения, но уведомления не уходят | Перезапустить узел; повторяется — сеть до базы |
| `ВСЕ узлы недоступны` | Сервис не работает целиком | Сначала база и VPS-1, потом узлы |
| `🔴 … отдаёт ключ НЕ из набора пинов` | Приложение уже не подключается | [15.3](#153-пин-не-совпадает-сертификат-истекает) |
| `публичный сертификат истекает…` | Продление не сработало | `journalctl -u aegis-cert`, затем `aegis-cert.sh renew --force` |
| `срок набора пинов…` | Скоро Android перестанет проверять пины | Релиз с новой датой (cert-pin-rotation.md) |
| `🔴 изменились файлы: …` | Бинарь подменён | Если не ваше обновление — [15.6](#156-взлом-машины) |
| `слушают неожиданные порты` | Новая служба или чужая программа | `ss -lntp` — кто это |
| `вход по SSH — …` | Кто-то вошёл | Не вы — [15.6](#156-взлом-машины) |
| `резервной копии нет больше суток` | Копии не снимаются | `journalctl -u aegis-backup` |
| `нужна перезагрузка…` | Обновление ядра ждёт | Перезагрузить в тихое время, узлы по одному |
| `сертификат … истекает меньше чем через 30 дней` | Внутренний сертификат | Перевыпустить (`internal-ca.sh`), разложить, перезапустить |
| `монитор работает…` (раз в сутки) | Монитор жив | Нет сообщения — монитор мёртв: проверить |

**Оповещение — только при смене состояния**: «сломалось» и «починилось».
Отказ, длящийся час, дал бы тридцать одинаковых сообщений; их перестают
читать, и следующий настоящий отказ проходит незамеченным. Поэтому же
в текстах пороги, а не числа: «меньше 21 дня» приходит один раз,
а «через 19, 18, 17 дней» — каждый день.

### 10.4. Ручка `/health`

```json
{ "version": "0.1.0", "uptime_seconds": 86400,
  "database": true, "listener": true, "listener_reconnects": 0 }
```

Состояние **процесса**, не пользователей. При `database: false` или
`listener: false` — код 503, и nginx убирает узел из ротации
(`max_fails=2 fail_timeout=10s`). Растущий `listener_reconnects` —
нестабильная связь с базой: не отказ, но признак.

### 10.5. Если нужен график

Только **blackbox** (спрашивает «отвечает ли ручка» — и всё), не экспортёр
приложения: тот собрал бы всё, что отдаёт цель, а стоит однажды добавить
в `/health` счётчик активности — и он окажется в графиках навсегда.

```yaml
scrape_configs:
  - job_name: aegis-health
    metrics_path: /probe
    params: { module: [http_2xx] }
    static_configs:
      - targets: [https://10.0.0.1:8443/health, https://10.0.0.2:8443/health, https://10.0.0.3:8443/health]
    relabel_configs:
      - { source_labels: [__address__], target_label: __param_target }
      - { source_labels: [__param_target], target_label: instance }
      - { target_label: __address__, replacement: 127.0.0.1:9115 }
```

**Чего в метриках нет и не будет:** числа подключённых устройств,
размера очереди, количества аккаунтов, частоты запросов.

## 11. Шаг 8. Резервные копии

### 11.1. Настройка (VPS-4)

```bash
sudo install -m 755 /tmp/aegis-deploy/{backup.sh,restore.sh,rotate-backup-key.sh} /opt/aegis/
# Публичная часть age-ключа (age1…) — из шага 3.2
echo 'age1…' | sudo install -m 644 /dev/stdin /etc/aegis/backup-recipient
printf 'AEGIS_BACKUP_KEEP=14\n' | sudo install -m 644 /dev/stdin /etc/aegis/backup.env
sudo install -m 644 /tmp/aegis-deploy/systemd/aegis-backup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now aegis-backup.timer
sudo systemctl start aegis-backup && ls -la /var/backups/aegis/      # aegis-….sql.age
```

Копия снимается от `postgres` через сокет (пароль нигде не лежит),
шифруется **до** того, как ляжет на диск, открытый дамп затирается
(`shred`) при любом исходе — даже если шифрование не удалось.

🔐 **На сервере — только публичная часть ключа.** Машина, делающая
копию, не должна уметь её прочитать: иначе взлом сервера даёт и текущие
данные, и всю историю.

### 11.2. 🔐 Что НЕ попадает в копию

**Конверты (`envelopes`).** Они удаляются сразу после доставки, и это
не оптимизация, а обещание: сообщение не хранится на сервере. Копия
вернула бы к жизни то, что пользователь считает удалённым, и сделала бы
изъятие копии равносильным изъятию переписки. Цена: при восстановлении
недоставленные сообщения теряются — отправители сочтут их отправленными,
получатели не увидят. Это лучше, чем хранить дольше обещанного.

**Вложения (`attachments`)** — по той же причине: живут тридцать суток,
а копия — ещё до четырнадцати. Вместе с ними пережила бы срок и строка
«кто загрузил».

Скрипт проверяет это сам и отказывается создавать копию, если данные
этих таблиц в неё попали.

### 11.3. Копия вне машины

Копия на том же диске, что и база, не переживает ни отказа диска, ни
изъятия машины. Забирать **с** машины администратора (а не отправлять
с сервера: у сервера не должно быть доступа к хранилищу копий):

```bash
# на машине администратора, раз в сутки
rsync -a --delete alice@vps4:/var/backups/aegis/ ~/aegis-backups/
```

Копии зашифрованы, так что хранилище может быть любым — но лучше своим.

### 11.4. Восстановление

```bash
# 1. Остановить всех, кто держит соединения с базой
sudo systemctl stop aegis-server                       # на КАЖДОМ узле
sudo systemctl stop aegis-admin aegis-reports.timer    # VPS-4

# 2. Прежнюю базу — не удалять, а отложить, пока восстановление не проверено
sudo -u postgres psql -c "ALTER DATABASE aegis RENAME TO aegis_before_restore_$(date +%Y%m%d)"
sudo -u postgres createdb -O aegis aegis

# 3. Ключ — только на время восстановления (с машины администратора):
#      cat aegis-backup.key | ssh alice@vps4 'sudo install -m 600 /dev/stdin /root/aegis-backup.key'
#    Восстанавливать ролью aegis (спросит пароль): дамп без владельцев,
#    таблицы достанутся тому, кто подключён.
sudo AEGIS_BACKUP_AGE_KEY=/root/aegis-backup.key \
    /opt/aegis/restore.sh /var/backups/aegis/aegis-20261002-040000.sql.age
sudo shred -u /root/aegis-backup.key

# 4. Запустить всё обратно
sudo systemctl start aegis-admin aegis-reports.timer
sudo systemctl start aegis-server                      # на каждом узле
```

Узлы обязательно остановить: восстановление в работающую базу оставит
их с соединениями, указывающими на данные, которых больше нет.

⚠️ В пустую базу, не поверх: дамп создаёт таблицы, и поверх существующих
восстановление откатится целиком (`--single-transaction`). Отложенную
базу удалить (`dropdb`), как только узлы проверены: в ней конверты,
которые по обещанию не живут дольше доставки.

### 11.5. Ротация ключа копий — раз в полгода

```bash
sudo /opt/aegis/rotate-backup-key.sh       # на машине администратора
scp /etc/aegis/backup-recipient alice@vps4:/tmp/ && ssh alice@vps4 \
    'sudo install -m 644 /tmp/backup-recipient /etc/aegis/backup-recipient'
```

🔐 **Прежний ключ не удалять сразу:** копии, снятые им, читаются только
им. Скрипт печатает дату, после которой ключ станет ненужным, и при
каждом запуске показывает ключи, которые уже можно удалить. Старые копии
не перешифровываются: для этого пришлось бы расшифровать их все на диске.

### 11.6. Проверять, а не надеяться — раз в месяц

На **отдельной** машине:

```bash
createdb aegis_test
AEGIS_DB_NAME=aegis_test AEGIS_BACKUP_AGE_KEY=… ./restore.sh <файл>
psql -d aegis_test -c 'SELECT count(*) > 0 FROM accounts;'
dropdb aegis_test
```

Непроверенная копия — не копия: нечитаемой она оказывается именно тогда,
когда нужна.

## 12. Проверка перед запуском

Каждый пункт — командой, а не «вроде настроено».

**Машины**
- [ ] `sshd -T`: `passwordauthentication no`, `permitrootlogin no` — на всех
- [ ] `ufw status`: открыто только своё (таблица в 10.2) — на всех
- [ ] Снаружи недоступны: узлы `:8443`, база `:5432`, onion-вход `:8444`
      (`nc -zv -w3 <публичный-адрес> 8443` → отказ/таймаут)
- [ ] `ls /etc/aegis/credentials` — права `600 root` у всех файлов
- [ ] На серверах НЕТ: `ca.key`, запасного ключа TLS, приватного ключа age

**Узлы и база**
- [ ] `systemd-analyze security aegis-server.service` ≈ 1.0 на всех узлах
- [ ] `/health` всех узлов: `database:true, listener:true` (через `--cacert`)
- [ ] Без клиентского сертификата база отказывает
- [ ] `sha256sum -c /etc/aegis/checksums.sha256` — OK
- [ ] 🔐 Сервер не видит содержимого:
      `sudo -u postgres pg_dump aegis | grep -c "текст тестового сообщения"` → 0

**Балансировщик**
- [ ] `compute-pin.sh --host <домен>:443` = основной пин из `pins.txt`
- [ ] `aegis-cert.sh status`: ключ в наборе; `certbot.timer` выключен,
      `aegis-cert.timer` включён
- [ ] Чужое имя (SNI) — обрыв; `/health` снаружи — 404
- [ ] Журналов нет: `ls /var/log/nginx/` — пусто или не растёт после запросов
- [ ] 10 быстрых запросов к `/v1/discovery/username/x` → часть получает 429

**Приложение**
- [ ] В релизной сборке два **разных** настоящих пина; `expiration` ≥ 12 месяцев
- [ ] Onion-адрес вписан в сборку; приложение регистрируется через Tor
- [ ] Сообщение между двумя телефонами, подключёнными к **разным** узлам,
      приходит сразу (уведомления через базу работают)

**Наблюдение и копии**
- [ ] Тестовое оповещение дошло в Telegram со всех машин
- [ ] Остановить один узел → оповещение; запустить → «восстановился»
- [ ] `systemctl start aegis-backup` → файл `.sql.age`; восстановление на
      отдельной машине прошло
- [ ] Оффлайн-носитель: `ca.key`, запасной ключ TLS + копия основного,
      ключ age, `aegis-certificate-key`, пароль базы — и вторая копия
      носителя в другом месте

## 13. Регламент

**Каждый день** — ничего, если пришло «монитор работает, проблем нет».
Не пришло — выяснить, почему молчит монитор.

**Каждую неделю**
- Прочитать оповещения за неделю: нет ли повторяющихся «починилось
  само» — это проблема, которая ждёт своего часа.
- `rsync` копий на машину администратора (если не автоматически).

**Каждый месяц**
- Восстановить копию на отдельной машине (11.6).
- `apt list --upgradable` на всех машинах — автообновления ставят только
  безопасность; остальное — вручную, узлы по одному.
- Перезагрузки, которые ждут (`/var/run/reboot-required`).
- Свежая версия сервера? → [14](#14-обновление-сервера).

**Каждые полгода**
- Ротация ключа копий (11.5).
- Пересмотреть, кто имеет SSH-доступ: `authorized_keys` на всех машинах.
- Сменить токен админ-центра.

**Каждый год**
- Перевыпустить внутренние сертификаты (монитор напомнит за 30 дней).
- Плановая ротация пинов, если подходит `expiration`
  (`docs/ops/cert-pin-rotation.md`: два релиза, не меньше 30 дней между).
- Проверить оффлайн-носители: читаются ли.

## 14. Обновление сервера

**Узлы — по одному**, не все сразу: сервис работает, пока обновляется
каждый отдельный узел.

```bash
# 0. Если в выпуске есть миграция — сначала копия
ssh alice@vps4 'sudo systemctl start aegis-backup'

# 1. На каждом узле по очереди
scp server/target/release/aegis-server-api alice@vps2:/tmp/
ssh alice@vps2 'sudo install -m 755 /tmp/aegis-server-api /usr/local/bin/ && rm /tmp/aegis-server-api \
    && sha256sum /usr/local/bin/aegis-server-api | sudo tee /etc/aegis/checksums.sha256 \
    && sudo systemctl restart aegis-server && sleep 3 && systemctl is-active aegis-server'

# 2. Проверить /health узла, только потом — следующий
```

Суммы обновлять **в том же шаге**, что и бинарь: иначе монитор
справедливо сообщит о подмене.

⚠️ **Сервер и приложение с несовместимыми изменениями обновляются вместе.**
Пример: с e02c90c сервер принимает только подписи `AEGIS_AUTH_v2` (подпись
покрывает тело запроса) — старое приложение не проходит аутентификацию
на новом сервере, новое — на старом.

### Разовые шаги после отдельных миграций

**0005** (время в конвертах и вложениях огрублено до часа) и **0006**
(то же для подписанных предключей и жалоб) — один раз, на VPS-4:

```bash
sudo -u postgres psql aegis -c 'VACUUM FULL envelopes, attachments, signed_prekeys, sealed_sender_reports;'
```

🔐 `UPDATE` в Postgres не переписывает строку на месте: старая версия,
с точным временем, остаётся в файлах таблицы. Обычный `VACUUM` лишь
помечает место свободным; `VACUUM FULL` переписывает таблицу. Таблицы
небольшие, блокировка — секунды. ⚠️ Физические блоки прежнего файла этим
не затираются; от снятого ранее образа диска не защищает ничто.

## 15. Инциденты

Общее правило: **сначала остановить ущерб, потом разбираться.** Всё, что
сделано, — в журнал изменений плана (раздел 30): что, когда, почему.

### 15.1. Узел упал или «слушатель мёртв»

1. nginx уже убрал его из ротации — пользователи не страдают.
2. `journalctl -u aegis-server -n 50` на узле.
3. `systemctl restart aegis-server`. Служба в `failed` после пяти падений
   за минуту — это не «перезапустить ещё раз», а ошибка настройки:
   узел печатает, чего не хватает.

### 15.2. База недоступна

1. Все узлы отдают 503 — сервис стоит: сообщения не принимаются,
   пока база не вернётся.
2. VPS-4: `systemctl status postgresql`, `df -h`, `journalctl -u postgresql`.
3. Диск полон — удалить старые копии (`/var/backups/aegis`, они есть
   на машине администратора), не трогать каталог данных.
4. Данные повреждены — восстановление (11.4). Недоставленные сообщения
   потеряны: в копии их нет по замыслу.

### 15.3. Пин не совпадает, сертификат истекает

**Сертификат истекает** (`< 7 дней`): `sudo /opt/aegis/certbot/aegis-cert.sh renew --force`;
ошибка — в выводе certbot (DNS, порт 80, лимиты Let's Encrypt).

**🔴 Сервер отдаёт ключ не из набора пинов** — все установки без связи
прямо сейчас. Значит, кто-то поменял `/etc/aegis/tls/public/privkey.pem`
или конфигурацию nginx. `aegis-cert.sh status`; вернуть ключ из
оффлайн-копии, `aegis-cert.sh renew --force`. Если вы этого не делали —
это ещё и [15.6](#156-взлом-машины).

### 15.4. 🔴 Ключ TLS скомпрометирован

1. **Сразу** — на запасной ключ (его пин уже в приложении):
   ```bash
   # с носителя на VPS-1, на время команды
   sudo /opt/aegis/certbot/aegis-cert.sh switch-key /tmp/tls-backup-key.pem && shred -u /tmp/tls-backup-key.pem
   ```
   Клиенты с актуальной сборкой продолжают работать; со старой — нет.
2. Отозвать старый сертификат: `certbot revoke --cert-path <старый> --key-path <старый ключ>`
   (прежний ключ сохранён как `retired-…-privkey.pem`).
3. Новый запасной ключ оффлайн → его пин вторым в приложение →
   **внеочередной** релиз (`docs/ops/cert-pin-rotation.md`).

⚠️ Если запасного ключа не было или он утёк вместе с основным,
безопасного выхода нет — только релиз с новым пином и ожидание
обновлений. Именно это предотвращает запасной ключ оффлайн.

### 15.5. Утёк `AEGIS_CERTIFICATE_KEY`

Утёкшим ключом подделываются сертификаты отправителя: чужое запечатанное
сообщение приходит подписанным чьим-то именем. Safety number это ловит,
но не все его сверяют.

1. Новый ключ: `openssl rand -hex 32` → на **все** узлы
   (`/etc/aegis/credentials/aegis_certificate_key`) → перезапуск всех узлов.
2. Выданные сертификаты станут недействительными; клиенты перевыпустят
   их в течение суток — это и есть цена.
3. Найти, откуда утёк, — скорее всего это 15.6.

### 15.6. Взлом машины

Признаки: «изменились файлы», вход по SSH не от вас, неожиданный порт,
незнакомые процессы.

1. **Не выключать сразу**, если нужно понять, что произошло: снимок диска
   у хостера (и памяти, если умеет). Выключение стирает следы в памяти.
2. Отрезать машину: у хостера — сетевой доступ, оставить только консоль.
   Узел — убрать из `upstream` в nginx; база — сервис встанет, это
   осознанно.
3. **Считать скомпрометированным всё, что лежало на машине**, и заменить:

   | Машина | Что заменить |
   |---|---|
   | Узел | `AEGIS_CERTIFICATE_KEY` (15.5), пароль базы, сертификат клиента базы, сертификат узла |
   | VPS-1 | Ключ TLS (15.4), токен Telegram, onion-ключ (новый адрес → релиз) |
   | VPS-4 | Пароль базы, сертификат базы, токен админ-центра; содержимое базы — у злоумышленника |

   Внутренние сертификаты нельзя отозвать по одному (списка отзыва нет):
   при взломе любой машины — **новый внутренний центр** и перевыпуск всех
   сертификатов. Машин четыре, это час работы.
4. Машину — переустановить с нуля, не «вычищать».
5. Что было у злоумышленника на VPS-4: аккаунты, публичные ключи,
   недоставленные конверты (зашифрованы) и вложения младше 30 дней
   (зашифрованы). Переписки, ключей пользователей и адресов клиентов
   там нет — их сервер не хранит.

### 15.7. Изъятие или потеря машины

То же, что 15.6, пункты 3–5, без расследования. Плюс:

* Журналы с адресами не изымут — их нет. Это проверяемо (шаг 12).
* Копии на изъятой VPS-4 зашифрованы ключом, которого на ней не было.
* Пользователям — сообщить, что произошло и что это значит для них:
  содержимое переписки сервер не видит, но список аккаунтов — да.

### 15.8. Утёк токен админ-центра

Админ-центр слушает только петлю, и токен без SSH-доступа к VPS-4
бесполезен — но менять сразу:

```bash
read -rs TOKEN && printf '%s' "$TOKEN" | /usr/local/bin/aegis-server-admin hash-token \
    | sudo install -m 600 /dev/stdin /etc/aegis/credentials/admin_token_sha256; unset TOKEN
sudo systemctl restart aegis-admin
```

## 16. Границы: что эта схема не делает

**Не защищает от хостера с доступом к памяти.** Работающая машина держит
ключи в памяти; хостер, снимающий её образ, их получит. Шифрование диска
защищает выключенный диск, не включённую машину.

**Не делает базу отказоустойчивой.** VPS-4 — одна. Её отказ — простой до
восстановления из копии (потеря недоставленных сообщений — по замыслу).
Реплика добавила бы вторую машину со всеми данными — второе место, где
их можно изъять.

**Внутренние сертификаты не отзываются по одному.** При компрометации —
новый центр целиком (15.6).

**Восстановление копии проверяется вручную.** Автоматическая проверка
потребовала бы постоянно иметь на диске расшифрованную копию.

**Канал оповещений — посредник.** Telegram видит, когда и что ломалось
у сервера, — поэтому в оповещениях только состояние. Кому этого мало —
свой канал (почта на своём сервере, вебхук) через `AEGIS_NOTIFY_CMD`.
